# Синхронизация GDD с кодом

Код — авторитет реализованного поведения; `Documents/GDD/systems/<id>.md` — авторитет дизайнерского замысла. При расхождении правит **сторона, которая знает истину**, и помечает другую сторону `> DISPUTED:` с `Owner:`.

## Когда автор кода обязан править GDD

В **том же изменении** (commit/PR), если ты:

- **Меняешь поведение, описанное в `systems/<id>.md`** (system-файл указан в обратной ссылке модульного `CLAUDE.md`):
  - правишь соответствующий блок в system-файле;
  - расхождение глубже одной строки → ставишь `> DISPUTED:` с `Owner: design`;
  - обновляешь `last_synced: <today>` во frontmatter system-файла.
- **Реализуешь публичный тип/метод, покрывающий `status: todo` system**:
  - меняешь `status` на `in-progress` или `live`;
  - добавляешь файл в `code_refs:`;
  - обновляешь `last_synced`.
- **Удаляешь поведение**, описанное в system:
  - меняешь `status` на `deprecated`;
  - дописываешь причину в начало тела файла;
  - **не удаляешь файл** в этом же PR — отдельным позже.
- **Меняешь модульный `CLAUDE.md`** так, что меняется ссылочный контракт (например, переименовал тип, попавший в `code_refs` нескольких system):
  - проверяешь все system, ссылающиеся на этот модуль (`Grep 'Assets/Modules/<Module>/' Documents/GDD/systems/`), правишь `code_refs:`.

## Когда **не** обязан править GDD

- Тело приватного метода без изменения наблюдаемого поведения.
- Рефакторинг внутри публичного метода без изменения сигнатуры/контракта.
- Изменение публичного API внутри модуля без сдвига роли модуля и без изменения дизайнерских правил.
- Тесты.
- Косметика (using-сортировка, форматирование).

Это правило **не** требует «прочитать GDD перед каждой правкой кода». Только при изменении дизайнерски значимого поведения.

## Запреты

- Создавать новые `§3.x`-ссылки в свежих модульных `CLAUDE.md`. Только `Documents/GDD/systems/<id>.md` (опционально с `#anchor`). См. `module-docs.md`.
- Помечать `status: live`, не сверив **все** `code_refs` с фактом кода. Если сверять некогда — `in-progress`.
- Создавать `> DISPUTED:` без `Owner:` и без предложения по разрешению (см. `Documents/GDD/CLAUDE.md`, раздел «Маркеры»).

## Как читать GDD при правке кода

Если меняешь поведение, для которого нет `systems/<id>.md` — это сигнал **создать** его (`status: todo` или `in-progress`), а не работать без GDD-привязки. Стиль файла, frontmatter и маркеры — в `Documents/GDD/CLAUDE.md`.

Если поведение покрывается несколькими system (например, замыкание = `painting.md` + `territory.md`) — правишь все затронутые.
